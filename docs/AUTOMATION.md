# 자동화 운영 안내

Linux/macOS의 Python 3.9 이상과 Git으로 동작하며, GitHub Actions에서 예약 실행합니다.
모든 날짜와 마감은 `Asia/Seoul`(KST, UTC+09:00)을 기준으로 합니다.

## 시작하기

1. 저장소의 기본 브랜치를 `main`으로 사용합니다.
2. 저장소의 **Settings → Secrets and variables → Actions**에 `DISCORD_WEBHOOK_URL`을 등록합니다.
3. 운영 준비가 끝나면 코드와 워크플로를 `main`에 올립니다.
4. Actions가 활성화되어 있고 워크플로에 저장소 내용 쓰기 권한이 있는지 확인합니다. 브랜치 보호 규칙이 자동화 커밋을 막으면 폴더와 발송 기록을 저장할 수 없습니다.

웹훅 주소는 소스 코드나 문서에 넣지 않습니다. 로컬에서 실제 전송할 때도 환경 변수 `DISCORD_WEBHOOK_URL`로만 전달합니다.
공개 저장소이므로 회고 파일에는 공개할 수 있는 내용만 작성해 주세요.

## 명단 수정과 폴더 관리

[`study_config.py`](../study_config.py)의 `MEMBERS`에서 명단을 수정합니다. 이름은 폴더 이름으로 쓰입니다.

```python
MEMBERS = [
    "손수빈",
    "황수진",
    "이예나",
    "장지원",
    "최진영",
]
```

같은 파일의 `MEMBER_EMOJIS`에서 이름별 이모지를 지정합니다. 새 참여자의 이모지가 없으면 `DEFAULT_MEMBER_EMOJI`(`🐾`)를 사용합니다. `BOT_NAME`은 메시지에 표시되는 봇 이름과 인사말에 적용되며, 기본값은 **회고냥**입니다.

`sync`, `run` 또는 `status --send`를 실행하면 다음 규칙으로 폴더를 맞춥니다. `status`, `preview`, `schedule` 미리보기는 파일을 변경하지 않습니다.

- 명단에 있는 사람의 폴더가 없으면 새로 만듭니다.
- 기존 폴더와 회고 파일은 그대로 유지합니다.
- 관리 중이던 사람이 명단에서 빠지면 폴더를 `[종료] 이름`으로 변경해 기록을 보존합니다.
- 같은 종료 폴더 이름이 이미 있으면 `(2)`, `(3)`을 붙여 덮어쓰지 않습니다.
- 같은 사람이 다시 명단에 들어오면 보관된 폴더를 복원합니다.
- 이름 충돌 등 자동으로 안전하게 처리할 수 없는 경우에는 덮어쓰지 않고 오류를 냅니다.

관리 기록은 [`.study/state.json`](../.study/state.json)에 저장합니다. 기록이 없는 기존 폴더는 이름이 **한글 2~10자**이고 실제 날짜 형식의 `YYYY-MM-DD` 하위 폴더가 있을 때만 참가자 폴더로 인식합니다. 다른 용도의 폴더에는 이 조합을 피해주세요. 이동할 경로 전체를 먼저 검사하고, 적용 중 오류가 나면 이번 실행에서 옮긴 폴더를 복구합니다.

시작일 전 첫 실행에서는 각 사람 아래 `2026-10-04/` 폴더를 만듭니다. 이후 실행에서는 가장 가까운 아직 마감되지 않은 회차의 폴더를 보충합니다. 각 마감일 **00:00**에는 다음 회차 날짜 폴더도 만듭니다.
이때 현재 회차의 폴더는 유지되므로 그날 23:59까지 계속 제출할 수 있습니다. 마지막 회차 뒤에는 새 회차를 만들지 않습니다.
빈 폴더를 Git에 보관하기 위한 `.gitkeep`은 자동으로 생성되며 제출 판정에서는 제외합니다.

명단 변경은 다음 실행부터 적용되며, **최종 결과의 대상도 실행 시점의 `MEMBERS`**입니다. 진행 중인 회차의 명단은 최종 결과 발송 후 변경하는 것을 권장합니다.

## 알림 일정

전체 알림 시각은 [`.study/schedule.json`](../.study/schedule.json)에 한국 시간으로 기록되어 있습니다. 실제 실행 일정은 `study_config.py`에서 계산합니다. 날짜 설정을 바꾸면 `python3 scripts/study.py schedule > .study/schedule.json`으로 이 목록을 갱신하고, 워크플로의 UTC cron 날짜도 맞춰 주세요. 명단만 수정할 때는 일정을 바꿀 필요가 없습니다.
한 회차당 아래 다섯 번, 총 35개의 일정입니다.

- **D-3 00:00:** 마감 3일 전 안내와 현재 제출 현황
- **D-2 00:00:** 마감 2일 전 안내와 현재 제출 현황
- **D-1 00:00:** 마감 1일 전 안내와 현재 제출 현황
- **D-day 00:00:** 오늘 23:59 마감 안내와 현재 제출 현황, 다음 회차 폴더 생성
- **D+1 00:00:** 마감 시점을 기준으로 최종 제출 결과 안내

예를 들어 첫 회차의 제출 기한은 `2026-10-04 23:59 KST`입니다.
10월 1~4일 00:00에 안내하고, 10월 5일 00:00에 최종 결과를 안내합니다.
마지막 최종 결과 일정은 `2026-12-28 00:00 KST`입니다.

수동 실행은 위 일정과 별개로 **이번 회차 마감일과 참여자별 제출 현황**을 보냅니다. 리마인드 날짜나 마감일에 실행해도 일반 현황 메시지를 보내며, 예약 알림의 발송 기록에는 영향을 주지 않습니다. 스터디 종료 후에는 종료 안내와 마지막 회차의 마감 기준 제출 결과를 보냅니다.

### 자정 실행의 정확도

자정은 목표 시각입니다. GitHub Actions는 부하에 따라 예약 실행이 지연되거나 누락될 수 있어 **00:00 정각 도착을 보장하지 않습니다**.
예약 워크플로는 기본 브랜치에서 실행되며, 공개 저장소는 60일간 활동이 없으면 예약 실행이 비활성화될 수 있습니다.
관련 동작은 [GitHub의 예약 실행 문서](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)에 설명되어 있습니다.

## 제출 판정

`이름/회차마감일/` 안에서 회고 글이 있는 **`.md`, `.txt`, `.html`, `.pdf`** 파일을 찾습니다. 하위 폴더도 검사하며, 하나 이상 인정되면 제출로 표시합니다.
다음 항목은 제출로 인정하지 않습니다.

- 코드·이미지·압축 파일 등 위 네 형식 이외의 파일
- `.gitkeep`을 비롯한 숨김 파일, 숨김 폴더 안의 파일, 심볼릭 링크
- 크기가 0인 파일
- 텍스트 파일에서 공백·줄바꿈·제어 문자·보이지 않는 문자만 있는 경우
- HTML 주석(`<!-- ... -->`)만 있는 파일이나 제목·빈 태그·스크립트·스타일만 있는 HTML 파일
- 비어 있거나 손상된 PDF, 암호화된 PDF, 이미지만 있는 PDF

Markdown·텍스트·HTML은 UTF-8로 저장해 주세요. HTML은 `head`, `script`, `style`, 주석, 태그를 제외한 본문 글을 검사합니다. PDF는 `pypdf`로 텍스트를 추출하며, 한 페이지 이상에 글자가 있어야 합니다.
자동화는 글의 존재를 확인하며 학습 내용의 충실도까지 평가하지는 않습니다.

마감 전 알림과 진행 중인 회차의 수동 현황(미리보기 포함)은 현재 체크아웃의 파일을 검사합니다. 로컬 미리보기에는 아직 커밋하지 않은 파일도 포함될 수 있습니다.

### 마감 뒤 제출 처리

최종 결과는 Git 기록에서 마감 이전의 상태를 찾아 검사합니다. 실행이 지연되어도 실행 시점의 최신 파일로 마감 결과를 판정하지 않습니다.
운영 브랜치 `main`의 첫 번째 부모 이력과 커미터 시각을 사용해, 마감 다음 날 00:00 미만의 가장 가까운 조상 커밋을 검사합니다. 마감일 23:59:59의 커밋까지 포함됩니다. 전체 Git 이력이 필요하며, 커밋되지 않은 파일과 심볼릭 링크·서브모듈은 제외합니다.

로컬 최종 결과 미리보기는 현재 체크아웃의 이력을 사용하므로, `main`에서 최신 전체 이력을 받은 뒤 확인합니다.

Git 커밋 시각은 GitHub 서버의 실제 업로드 시각과 다르며 사용자가 바꿀 수도 있습니다. 예를 들어 마감 전에 만든 커밋을 마감 뒤에 푸시한 경우, Git 기록만으로 실제 업로드가 늦었음을 증명할 수 없습니다.
회고는 반드시 마감 전에 `main`에 반영하고, 업로드 시각에 이견이 있으면 GitHub 활동 기록을 포함해 운영자가 확인합니다.

## 로컬 확인

저장소 루트에서 실행합니다. 최초 실행 전에 PDF 판정에 필요한 패키지를 설치합니다. 미리보기와 폴더 동기화에는 웹훅이 필요하지 않습니다.

```sh
python3 -m pip install -r requirements.txt
```

```sh
# 명단에 맞춰 로컬 폴더와 관리 기록 갱신: 커밋·푸시 없음
python3 scripts/study.py sync

# 일반 현황 메시지 확인: 파일 변경·실제 전송 없음
python3 scripts/study.py status

# 오늘 예정된 예약 알림 확인: 파일 변경·실제 전송 없음
python3 scripts/study.py preview

# 전체 일정 JSON 출력: 파일 변경 없음
python3 scripts/study.py schedule

# 로컬 폴더 동기화 후 오늘의 알림 출력: 실제 전송 없음
python3 scripts/study.py run
```

일반 현황을 실제로 보내려면 아래 명령을 사용합니다.

```sh
python3 scripts/study.py status --send --persist
```

오늘 예정된 예약 알림을 보내려면 아래 명령을 사용합니다.

```sh
python3 scripts/study.py run --send --persist
```

`--send`는 Discord 전송을 활성화합니다.
`--persist`는 `--send`와 함께 사용하며, 폴더와 발송 상태를 Git에 커밋하고 `origin`에 푸시합니다. **미커밋 변경이 없는 `main` 전용 체크아웃**에서 실행해야 합니다. 실제 실행 전에는 전체 Git 이력과 원격 쓰기 권한을 확보합니다.

`--send`만 사용하고 `--persist`를 생략하면 실제 전송은 하지만 관리 기록은 로컬에만 남습니다. 새 체크아웃으로 옮기거나 로컬 상태를 지우면 중복 발송될 수 있으므로, 운영에는 `--persist`를 사용합니다.

## 재실행과 전송 실패

[`.study/state.json`](../.study/state.json)의 `events`에는 예약 일정별 발송 기록을, `manual`에는 수동 현황 발송 기록을 따로 남깁니다. `--persist` 운영에서는 발송 전에 `pending` 상태를 원격 저장소에 먼저 저장하고, Discord 응답을 확인한 뒤 `sent` 상태와 메시지 ID를 저장합니다.
완료된 예약 일정은 재전송하지 않습니다. 수동 **Run workflow**는 새로 실행할 때마다 현황을 보내지만, 같은 실행의 **Re-run jobs**는 이미 보낸 현황을 다시 보내지 않습니다. 전송 중 연결이 끊기거나 응답 확인에 실패하면 실제로 도착했는지 판단할 수 없어 `pending` 기록을 남기고 실행을 중단합니다.

예약 실행(`run`)은 **한국 시간으로 오늘 예정된 일정만** 처리합니다. 다음 날까지 놓친 일정은 자동으로 몰아서 보내지 않습니다. 복구가 필요하면 운영자가 `schedule` 출력에서 ID를 확인해 명시적으로 선택합니다.

```sh
# 이미 예정 시각이 지난 첫 회차 최종 결과를 복구하는 예시
python3 scripts/study.py run --send --persist --event 2026-10-04:final
```

`pending` 기록이 있으면 위 명령도 바로 재전송하지 않습니다. 먼저 실행 로그와 Discord 채널을 확인한 뒤 다음과 같이 처리합니다.

1. **이미 도착한 경우:** 해당 이벤트의 `status`를 `sent`로 바꾸고 실제 `message_id`를 기록합니다.
2. **도착하지 않은 것이 확인된 경우:** 예약 알림은 `events`, 수동 현황은 `manual`에서 해당 ID의 기록 하나만 삭제한 뒤 재실행합니다.
3. 수정한 상태 파일을 `main`에 커밋·푸시한 뒤, 전용 체크아웃에서 변경 사항을 받은 상태로 실행합니다.

기록을 확인 없이 지우면 중복 알림이 생길 수 있습니다. 네트워크 장애까지 포함해 “항상 정확히 한 번 전송”을 보장하지 않습니다.

코드가 `main`에 올라가기 전에는 GitHub Actions 자동화가 시작되지 않습니다. 저장소 생성과 웹훅 Secret 등록만으로 알림이 발송되지는 않습니다.

## GitHub Actions에서 운영하기

[Study automation](../.github/workflows/study.yml)은 다음과 같이 실행됩니다.

- **예약 시각:** 35개 일정에 맞춰 폴더를 동기화하고 Discord 알림을 보냅니다.
- **설정·스크립트 변경을 main에 반영:** 폴더만 동기화합니다. 알림을 추가로 보내지 않습니다.
- **Actions → Study automation → Run workflow:** 기본값 `send`로 실행하면 어느 날이든 일반 현황 메시지를 보냅니다.

수동 실행의 `mode`는 다음과 같습니다.

- **`send` (기본값):** 폴더를 동기화하고 이번 회차 마감일과 제출 현황을 Discord로 보냅니다.
- **`preview`:** 일반 현황 메시지를 실행 로그에서 확인합니다. 파일 변경과 실제 전송은 없습니다.
- **`sync`:** 폴더와 관리 기록만 동기화합니다. 알림은 보내지 않습니다.
- **`replay`:** 놓친 예약 알림을 복구합니다. `event_id`에 `2026-10-04:final`처럼 일정 ID를 반드시 입력합니다.

`event_id`는 `replay`에서만 사용합니다. 예약 실행은 수동 모드와 관계없이 기존 일정대로 동작합니다.
`sync --persist`는 알림 없이 폴더 변경만 커밋·푸시하는 운영 명령입니다.
워크플로의 동시 실행 제한과 로컬 실행 잠금으로 작업이 겹치지 않도록 합니다.
실행 중 원격 `main`이 바뀌면 자동 병합하거나 덮어쓰지 않고 실패합니다. 최신 코드를 받은 뒤 다시 실행해 주세요.

### 별도 서버에서 실행하기

GitHub 예약 대기열을 거치지 않으려면 계속 켜져 있는 Linux 서버에서도 같은 스크립트를 실행할 수 있습니다.
서버의 시간대를 `Asia/Seoul`로 설정하고, 전용 체크아웃과 실행 환경의 `DISCORD_WEBHOOK_URL`, Git 쓰기 자격 증명을 준비합니다.
서버 cron 예시는 다음과 같습니다. 경로는 실제 체크아웃 위치로 바꿔 주세요.

```cron
0 0 * * * cd /srv/cs-study-notes && git pull --ff-only origin main && python3 scripts/study.py run --send --persist
```

이 cron은 서버 시간대를 따릅니다. 서버 재시작·네트워크 장애 등까지 포함한 정확한 도착 시각을 보장하지는 않습니다.
실행 경로는 하나만 선택하세요. 서버를 사용할 때에는 GitHub 예약 발송을 끄고, 웹훅 값을 crontab이나 저장소에 직접 적지 마세요.
